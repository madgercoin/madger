# MADGER implementation and release checklist

Use this checklist for every production change. Mark only applicable items in the pull request or release record; do not edit this master into a one-off task log. MADGER favors a deliberate, reviewable release over a fast release.

## 1. Scope and truth

- [ ] The change has a clear user/community benefit and is the smallest maintainable solution.
- [ ] Claims were verified against repository code, approved project decisions, or official channels—not inferred from a roadmap or placeholder.
- [ ] Current capabilities, proposals, and long-term aspirations are clearly distinguished.
- [ ] No text implies guaranteed returns, price performance, partnership, listing, launch date, payment capability, or utility.
- [ ] Unresolved requirements are recorded under **Future Decisions** rather than filled with invented details.
- [ ] Relevant contributor documentation and public content are updated together.

## 2. Brand and content

- [ ] `MADGER`, `$MADGER`, the Honey Badger character, and The Burrow are named consistently.
- [ ] Tone communicates resilience, confidence, determination, attention to detail, dry humor, and community without hostility or manufactured hype.
- [ ] Existing approved imagery and the ink/bone/gold visual system are preserved; any new asset has documented provenance and usage rights.
- [ ] Text is concise, proofread, and understandable without crypto jargon.
- [ ] Official links match the repository: `madgercoin.com`, `x.com/madgercoin`, `t.me/madgercoin`, and `t.me/madgerburrow`.
- [ ] Homepage, litepaper, metadata, FAQ, safety copy, roadmap, and social announcements do not contradict one another.

## 3. Token and financial safety

- [ ] Public content states that MADGER is minted but not publicly launched for trading and reproduces the official mint exactly: `BHauMX8akk2umqkQqnJwpYkCRkZmefGnEBFByeFXRKqv`.
- [ ] Any token values are explicitly labeled proposed until formally approved; launch method, supply, allocation, vesting, authority, liquidity, and treasury claims have an auditable source.
- [ ] A mint address is never accepted from a direct message or unverified contributor and is checked character by character by multiple authorized reviewers.
- [ ] If launched, the exact address and final disclosures are prepared for simultaneous publication on the website, official X account, and Telegram announcement channel.
- [ ] Risk language remains visible and avoids financial, legal, or tax advice.
- [ ] No secret, seed phrase, private key, wallet credential, API token, personal data, or private operational address is present in source, history, build output, screenshots, or logs.

## 4. Implementation quality

- [ ] Production work targets the root static files; no obsolete starter content is reintroduced.
- [ ] New/renamed/removed production files are reflected in `build.mjs`; public URLs, canonical tags, navigation, sitemap, manifest, and 404 behavior are reviewed where relevant.
- [ ] HTML remains semantic with logical landmarks/headings, unique IDs, correct labels, and safe external-link attributes.
- [ ] All functionality works with keyboard only; focus is visible; controls expose state; decorative images are hidden and informative images have useful alternatives.
- [ ] Color contrast, zoom/reflow, touch-target size, screen-reader announcements, and `prefers-reduced-motion` behavior have been considered.
- [ ] Responsive layouts work without horizontal overflow at narrow/mobile, tablet, desktop, and zoomed viewport sizes.
- [ ] Images have suitable dimensions/format/compression and safe crops; added code or third-party resources have a justified performance cost.
- [ ] User-controlled data is not introduced without validation/encoding, privacy review, and a threat model; no unnecessary analytics, tracking, wallet request, or external script is added.
- [ ] `_headers` protections and cache consequences are reviewed. Replaced assets with immutable caching receive a new filename when immediate propagation matters.

## 5. Programmatic verification

- [ ] Clean dependency install succeeds: `npm ci`.
- [ ] Production artifact builds from scratch: `npm run build`.
- [ ] `dist/` contains exactly the intended allowlisted pages/assets and no secrets, legacy starter, or unreviewed file.
- [ ] Cloudflare dry run succeeds: `npm run check`.
- [ ] Internal root-relative references resolve in the built artifact.
- [ ] Changed HTML, CSS, JavaScript, JSON, XML, and headers have been syntax/format checked with an appropriate validator.
- [ ] Any warning is understood and recorded; only unavoidable environment-only proxy notices are accepted.

## 6. Visual and interaction QA

- [ ] `VISUAL_QA.txt` has been completed for affected views and relevant screenshots are attached to review.
- [ ] Homepage, litepaper, 404 page, mobile navigation, outbound links, FAQ, Daily Dig, and footer year behave as expected.
- [ ] Logo/mascot artwork is not stretched, clipped, recolored, obscured, or placed without safe margins.
- [ ] Metadata/social-card preview, favicon, install manifest, print view of the litepaper, and missing-route experience are checked when affected.
- [ ] Browser console and network panel show no unexpected errors or requests.

## 7. Release and operations

- [ ] Reviewed commit SHA and previous known-good deployment are recorded.
- [ ] Preview is approved before production; concurrent or out-of-order deployments are prevented.
- [ ] The authorized release path in `README_DEPLOY.txt` is followed.
- [ ] Production HTTPS, critical URLs, official outbound links, response headers, cache behavior, desktop/mobile layout, and accessibility interactions pass smoke testing.
- [ ] Rollback is performed instead of improvising a rushed fix if a critical check fails.
- [ ] Security/content incidents are corrected through official channels and documented without leaking sensitive information.

## 8. Token launch gate (not yet satisfied)

- [ ] Final launch method, network details, token name/ticker/supply/decimals, allocations, vesting, authorities, liquidity, and material risks are approved and published.
- [ ] Creator, treasury, and operations responsibilities are separated with reviewed custody, backup, access, and incident-recovery procedures.
- [ ] Contract and metadata are independently verified; a small test transaction and launch rehearsal have completed safely.
- [ ] Website and litepaper have passed legal/compliance review appropriate to the operating jurisdictions.
- [ ] Official-channel publication and impersonation/scam response are rehearsed before funds or addresses are public.

## 9. Future utility gate

Before adding wallets, commerce, or real-world crypto payments:

- [ ] A real user need, measurable success criteria, maintenance owner, and sustainable operating model are approved.
- [ ] Regulatory, tax, consumer-protection, sanctions, privacy, accessibility, and geographic requirements receive qualified review.
- [ ] Custodial/non-custodial boundaries, transaction finality, refunds, pricing/volatility, fees, supported assets/networks, and merchant/user support are designed explicitly.
- [ ] Threat modeling covers wallet impersonation, address substitution, malicious signing, dependency/supply-chain risk, fraud, abuse, key compromise, and provider outage.
- [ ] The system is tested in a non-production environment, audited where appropriate, monitored, documented, and supported by rollback/incident procedures.

## Future Decisions

- Required reviewers, merge/release authority, branch protections, CI checks, browser/device support matrix, and formal definition of done.
- Token launch facts and governance/custody controls listed above.
- Legal entity, project jurisdictions, contributor/code/asset licensing, privacy terms, and security contact/disclosure policy.
- Scope and architecture for analytics, community submissions, wallet features, payments, merchant tooling, APIs, or other ecosystem utility.
